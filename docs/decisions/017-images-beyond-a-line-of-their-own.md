# 017 — Images in a sentence, a list item or a quote, and a width the host chooses

> **Summary.** `imageSource` also draws a Markdown image that sits in a sentence, a list item or a quote, as an inline slot, and every drawn image is capped at its column. Two new props let the host choose how far a picture may spill past the column to the editor's width (`imageWidth`) and where a narrower one sits (`imageAlign`). It costs a second slot shape on the canvas, a table-cell and a linked-image gap that the docs state, and a layout rule that the spike proved on the canvas only.

Accepted by the owner on 2026-10-16, with the spike's result and its one change recorded in the amendment below: `imageWidth: "wide"` on the canvas only, `preview` and `split` kept at the column, `imageAlign` on both. The picks marked "for the owner to confirm" (a table cell stays literal on the canvas; a linked image stays as source), the names `imageWidth`, `imageAlign` and their values, and the 1rem gutter stand as written.

## Context

ADR-014 draws an image only when it is alone on its line as a top-level paragraph. Its Consequences leave "images inside a sentence and images in a table cell on the canvas" open, and its Alternatives rejected defer inline widgets "when the lone-line version is in use and a host asks". The owner asked for the three follow-ups listed after 0.23.2: images in a sentence, a list item or a table cell, and an image that goes beyond the text column. Facts below come from reading the code on 2026-10-16, not from running it.

- **Today the two surfaces agree by leaving these alone.** `remarkImage` (`src/render/remark-image.ts`) matches only a paragraph whose single child is an `image`. `buildImages` (`src/inplace/image.ts`) matches a line that is one image and a top-level paragraph by itself. Anything else is the source text on the canvas and the default `<img>` (with `react-markdown`'s URL filter) in `preview` and `split`.
- **The machinery for an inline slot exists.** `![[ref]]` mid-sentence already works on both surfaces (ADR-009): `remark-embed` splits a text node into a `<span>` carrier, and `embedField` emits a non-block `EmbedWidget` that registers an `inline: true` slot. `EmbedSlot` already carries `inline` and an optional `image`, and `Embed` already takes an `inline` prop, which `HostImage` wraps.
- **A table cell is a separate surface.** On the canvas the table widgets build their cells with `renderInline` (`src/inplace/inline-md.ts`), not through CodeMirror's decorations. ADR-009 settled `![[ref]]` in a cell as a documented non-goal: literal on the canvas, drawn in `preview` and `split`, with the whole-document pass skipping a `Table` node so the two never overlap.
- **A link around an image is a second click target.** In `[![alt](src)](url)` the canvas already handles clicks on the link, and a widget inside it would have to agree with that handling.
- **Nothing caps a drawn image.** `.stylo-image` in `src/styles/stylo.module.css` sets only a margin, and the canvas styles only the slot. The host's node is left alone, so a picture with a fixed width wider than its container overflows it.
- **Stylo has no text column of its own.** There is no column-width or measure token and no `max-width` on the editing surface; the column is the width the host gives Stylo's container. The canvas insets its content by `0.75rem` (`.cm-content` padding), and the scroller is the full width of the editor. A host that centres a narrow column inside a wide editor therefore leaves real room beside the column that belongs to Stylo's own box.
- **The owner's words on width:** the right behaviour depends on the style the host wants, and a column of text with an image that goes out of bounds is a creative layout worth allowing, so it should be a choice, not a rule.

## Decision

1. **Spike first, in real Chrome, before any code for point 6.** Prove the wide layout (point 6) on the canvas and in `preview`: a picture narrower than the column sits where `imageAlign` puts it, a wider one spills toward the open side (evenly when centred) up to the editor's width, clicks still land on the right line (CodeMirror measures a block's height, and horizontal overflow must not move it), and the scrollbar width is allowed for. If it cannot be made clean, ship points 2 to 5 and 7 and record the wide mode as deferred in an amendment, with the reason.
2. **Draw an image in any text content, not only alone on a line.** The rule is by node, on both surfaces: a Markdown image that `parseImage` accepts, outside code, outside a link, and outside a table cell on the canvas. A lone top-level image stays the block slot of ADR-014. Any other image (in a sentence, a list item, a quote) is an inline slot: a `<span>` carrier in `preview` and `split`, and a non-block replace widget on the canvas, built exactly as the inline `![[ref]]` is. The host returns phrasing content for these, as it does for an inline embed. Whether a heading is covered falls out of the node rule and is pinned by a test in the slice rather than assumed here.
3. **A line the caret touches shows its source,** for inline slots as for block ones: the existing reveal rule, which withholds every widget on that line. In a `readOnly` note nothing is withheld, as ADR-014's amendment settled for block widgets. The arrow-key stop of ADR-014 applies to block slots only; an inline slot is atomic to horizontal motion and needs no vertical stop.
4. **A table cell is drawn in `preview` and `split` and stays literal on the canvas.** The same trade as `![[ref]]` in a cell (ADR-009): the cell surface is for editing tabular text, and wiring the imperative table widgets to the React registry is not worth the coupling. The docs state the parity gap. _Proposed, for the owner to confirm._
5. **A linked image stays as source on both surfaces.** `[![alt](src)](url)` is left to `react-markdown` and to the canvas's link handling, so the two surfaces stay equal and no click has two meanings. It becomes right when a host asks for badges. _Proposed, for the owner to confirm._
6. **Cap every drawn image at its column, and let the host choose a wider cap.** The slot's content gets `max-width: 100%` on all surfaces, so a picture never overflows the column unless the host asks. A new optional prop, `imageWidth?: "column" | "wide"`, defaults to `"column"`. A second optional prop, `imageAlign?: "left" | "center" | "right"`, defaults to `"left"` and places a block picture that is narrower than the column; the owner's words: expose center, left or right. With `"wide"`, a block slot's picture may grow up to the editor's width, spilling past the column toward the side its alignment leaves open (both sides when centred, to the right when left, to the left when right); the container width comes from CSS container query units on the scroller (`cqw`), not from measuring in JavaScript, and the choice reaches the CSS as an attribute on the component's root, so it is reactive and needs no remount. The slot itself stays column-wide, so the per-image `|full` of ADR-014 keeps meaning "fill the column" in both modes. An inline slot is never wide: it sits in a line. The value names are the owner's to settle; the point is that the host, not Stylo, picks the layout.
7. **No new dependency, no new `--stylo-*` token.** The caches, `invalidateImage`, the size convention and `onResolveError` are unchanged: an inline slot calls the same `imageSource` with the same `src` and `alt` and shares the same cache entries. No token is needed because the choice is a prop and a root attribute, and the cap is a fixed rule; if a token turns up, its reach on `preview` is decided in the same change (ADR-002 §3).
8. **Closing the slice** extends `remarkImage` and `buildImages` (the canvas file is 133 lines, so the inline pass goes in a new file under the 200-line ceiling, `src/inplace/image-inline.ts`), gives `EmbedSlot` and `HostImage` the inline path, adds `imageWidth` and `imageAlign` to the props, and writes the props reference, the wiki, a journal note and a CHANGELOG entry. Tests cover each place on both surfaces, the table-cell and linked-image gaps, `readOnly`, the caret reveal, the cap, and both `imageWidth` values and all three `imageAlign` values in a real browser. ADR-014 gets an amendment pointing here.

## Consequences

- **Easier.** A host that sets `imageSource` sees pictures wherever a note puts them, not only on their own line, and chooses how far a picture may go beyond the text. A consumer that never passes `imageSource` sees nothing change, and one that never passes `imageWidth` gets the column cap.
- **Harder.** A second slot shape (inline) sits beside the block one on the canvas, and the width rule is the one place Stylo styles a host's node. A host that gives a picture both a fixed width and a fixed height can still see it distorted when the cap applies, because the cap is `max-width` only. The wide mode depends on a layout the spike must prove, so this record stays `proposed` until it has.
- **Parity gaps by design.** A table cell on the canvas (which the table widget renders as it always has, with no picture), and a linked image on every surface, are not drawn as a picture, and `preview` and `split` differ from the canvas for a cell. The docs say so, and tests pin both.
- **Left open.** A reference-style image (`![alt][ref]`) and a raw `<img>` are not handled, since `parseImage` reads only the inline form. Drawing in a table cell on the canvas, a linked image, and a per-image wide form are each their own decision, with the conditions below.

## Alternatives rejected

- **Always let images break out of the column.** It forces one layout on every host, and the room beside the column exists only when the host leaves it. Becomes right if every consumer wants it, which the owner's own framing makes unlikely.
- **A `--stylo-image-max-width` token instead of a prop.** A token can set a width but cannot centre a picture on the column or read the editor's width, and the right values differ by mode. Becomes right if hosts want arbitrary widths such as `90vw` and are willing to own the centring.
- **Measuring the column in JavaScript (`ResizeObserver`).** It adds code to the part of the canvas where click and caret positions are sensitive to layout, for a number the CSS container units already give. Becomes right if the spike shows the CSS cannot place a narrower picture at the column edge, and then only for that one measurement.
- **A per-image wide form in the alt text (`|wide`).** Stylo does not parse the suffix, and a convention hosts must each implement is a cost they pay for a layout choice that is the same for every picture in a note. Becomes right if hosts copy the same parsing code, together with the exported size helper ADR-014 mentions.
- **Draw an image in a table cell on the canvas.** Full parity, but it wires the table widgets to the React registry. Becomes right if a host needs pictures in tables and accepts the coupling.
- **Draw a linked image.** Badges and linked thumbnails would render, but the link click and the picture need one agreed meaning. Becomes right when a host asks, with tests for the click.
- **Reuse the block slot for every image.** A block replace would hide a list marker or the text around a sentence's image. Never right for an image that shares its line with other content.

## Amendment (2026-10-16): the spike's result, and wide mode on the canvas only

Point 1's spike ran in real Chrome, on a page that mounted `<Stylo>` with the candidate CSS as the host's stylesheet, in a 700 px editor with a 420 px column (and in a 1,100 px one with a 640 px column). The decision above stands, with these details fixed.

- **The canvas is clean with CSS only.** `container-type: inline-size` goes on `.cm-scroller` (the context menu, the selection bar and CodeMirror's tooltips mount on `.cm-editor`, outside it, so layout containment reaches none of them), and only when `imageWidth` is `"wide"`, so a host on the default pays nothing. The slot becomes a flex row whose `justify-content` is `imageAlign`; the host node's wrapper (`.stylo-embed-content`) takes `flex: none`, `min-width: 100%` and a `max-width` (so it grows to its picture, between the column and the cap, and a host `width: 100%` still means the column), and its child takes `max-width: 100%`. A first version that left the wrapper column-wide and let the picture overflow it was defeated by a host `<img>` with its own `max-width: 100%`, as a Tailwind-style reset has. A narrow picture sits where `imageAlign` puts it, a wider one spills toward the open side up to the editor's edge, `scrollWidth` equals `clientWidth` at every alignment, a host `<img>` that carries its own `max-width: 100%` behaves the same, and clicks land on the right line, also after the editor is resized so that every picture changes height (CodeMirror remeasures when the scroller resizes).
- **`cqw` includes the scrollbar, so the cap holds back a fixed `1rem`.** A container query unit on a scroll box is its border-box width, scrollbar included (8 px in the spike, up to about 15 px elsewhere, 0 for an overlay bar), so a cap of `100cqw` overflowed by the bar and showed a horizontal scrollbar. The cap is `calc(100cqw - 1rem)` for `center` and `calc((100cqw - 1rem + 100%) / 2)` for `left` and `right`, where `100%` is the slot. The same margin shows as a little air beside a picture that spills, never as a scrollbar.
- **`center` and `right` assume a column centred in the editor.** The room beside the column is read as `(editor − column) / 2` on each side, so a host that leaves its column flush left sees a centred or right-aligned wide picture run off the left edge, where it cannot be reached. `left` degrades safely there, at a cap a little under the room it has. The props reference says so: choose `imageAlign: "left"` or leave `imageWidth` at `"column"` when the column is not centred.
- **`imageWidth: "wide"` is a canvas-only mode; `preview` and the preview pane of `split` stay at the column.** `.preview` is both the scroll box and the padded column, so a container query unit on it measures the column and nothing can spill. The unit works on the Stylo root, but `container-type` applies layout containment, which would make the root the containing block of the `position: fixed` toolbar, selection bar and menus. A wrapper inside `.preview` that carries the padding would work but changes the DOM that hosts style, and a host's own `.preview` padding override would then sit outside the container. The owner chose the canvas only, as the surface where hosts lay the page out; the parity gap is stated in the docs and pinned by a test.
- **`imageAlign` applies on every surface that draws a block picture.** Placing a narrower picture needs no container unit (a flex row and `justify-content`), so `preview`, `split` and the canvas agree on it. An inline slot ignores both props.
- **The choice reaches the CSS as two attributes on the component's root,** `data-stylo-image-width` and `data-stylo-image-align` (following the existing `data-stylo-mode`), so a change needs no remount. Consumers do not style these; they are the contract between the props and the stylesheet.
- **Still left open.** A column that is not centred with a wide centred or right picture, a wide mode for `preview`, and a distorted picture when a host gives it both a fixed width and a fixed height (the cap is `max-width` only).
- **One pass, in `image.ts`.** Point 8 put the inline pass in a new `src/inplace/image-inline.ts`. A review of the slice found that two passes derived the same answer twice (each walked the line, and the block pass re-read what the inline pass had already classified) and that the split existed only to avoid an import cycle. `buildImages` now visits each line that holds `![` once and classifies every `Image` node: a top-level paragraph by itself is a block slot, any other is an inline one. `image.ts` is 151 lines, and `ImageWidget` stays in it.
- **Code never needs skipping.** Parsed by the Markdown grammar, an inline code span, a fenced block and an indented block contain no `Image` node, so only a table and a link are skipped.
- **Trailing spaces do not make a picture inline.** `![a](b)` followed by spaces on its line is still an image alone in its paragraph (Lezer's paragraph range includes them), so it is a block slot on the canvas as it is in `preview`, and the block slot replaces the whole line.
